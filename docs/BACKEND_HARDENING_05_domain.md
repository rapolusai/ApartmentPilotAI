## Database evidence (cloud container, PostgreSQL, 9 Oct 2026)
- Fresh database: `mvn clean test` **79 run, 0 failures, 0 errors** (67 existing + 12 new).
- Detection: with this branch's `src/main` Java reverted, the 12 new tests failed (9 failures, 3 errors). V12 was still on disk in that run, so the self-approval failed at the database instead.
- `NOT VALID` upgrade path: a database holding a historic self-approved `APPROVED` row (constraint dropped, V12 history row removed) re-ran V12 through Flyway. The migration applied, the historic row is unchanged (`convalidated=false`), and the full suite passed again (79/79).

## Migration numbering
V12 was chosen per the proposal because V11 is claimed by the PIN-login thread. Flyway's default `outOfOrder=false` means: if a database receives V12 first and V11 is merged later, Flyway validation will refuse to start ("resolved migration not applied"). Merge V11 before deploying V12, or renumber before merge. Do not edit an applied migration.

## Not done / decisions
- Reversal of a payment by its own submitter/approver is out of scope (the proposal says so).
- A contact `kind` change is allowed even when the contact is linked as a vendor on tickets, services or recurring templates. Existing links stay. New links still require an active VENDOR for recurring templates.
- Phone numbers are validated but not re-formatted. Existing stored invalid numbers are not rewritten.
